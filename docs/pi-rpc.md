# Pi RPC transport and lifecycle evidence

The application includes a main-process RPC client for **Pi 0.85.1** and an opt-in installed-CLI lifecycle probe. The native probe passes on macOS arm64 using `@earendil-works/pi-coding-agent@0.85.1` installed separately from application dependencies. This completes the local V5 probe; it does not enable Pi in the desktop UI or pass the C4 delivery gate.

## Transport behavior

`PiClient` uses LF-delimited JSON with strict UTF-8 and a 1 MiB frame limit. CRLF is accepted; U+2028/U+2029 remain text inside a record. Command IDs are generated by the client. Responses must match both ID and command; unrelated events are not mistaken for responses even when they contain an ID. Malformed, duplicate, foreign, or mismatched responses close the connection.

Events are delivered in wire order. A command response is returned only after earlier event callbacks finish. The event callback is intended for normalization/persistence and must not wait for user input. Bounds cover pending requests, event count/bytes, dialogs, request deadlines, and dialog deadlines. Timeout, protocol failure, or failed event persistence closes the client and triggers owned process-group cleanup. Native error text is not included in `PiFailure`.

Extension dialogs have a separate asynchronous handler, so a waiting dialog does not block state queries or cancellation. Select answers must be offered options; confirm, input, and editor responses retain their distinct formats. Cancellation and expiry invalidate outstanding responses, including an answer queued behind stdin backpressure. A handler failure stops the connection without sending an affirmative response. Fire-and-forget extension notifications remain native events; unknown dialog methods fail explicitly.

The client is not an IPC API. Native records and dialog contents are untrusted, potentially sensitive main-process data. A runtime adapter must validate event-specific shapes, redact known secrets, establish session/turn ownership, and normalize events before journaling or displaying them. The transport alone does not enforce tool permissions, classify terminal outcomes, or verify restored session identity.

## Observed lifecycle differences

The [versioned RPC contract](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/docs/rpc.md) distinguishes prompt acceptance from asynchronous completion. The native probe confirms these cases:

| Operation                           | Observed result                                                                                         | Adapter requirement                                                                                        |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Normal prompt                       | Acceptance precedes streamed events and final settlement                                                | Keep the application turn active after the response                                                        |
| Provider rejection after acceptance | Assistant message ends with `stopReason: error`; the agent settles                                      | Report failure from terminal events; do not invent a second prompt rejection                               |
| Streaming cancellation              | `clear_queue` followed by `abort` produces an aborted assistant message and an idle state               | Preserve cancellation outcome and ensure no queued continuation remains                                    |
| Native restoration                  | `switch_session` restores the same ID and messages from the retained session file after process restart | Verify identity, inputs, model, and cwd before calling it a resume                                         |
| Extension command with a dialog     | The command can be handled successfully without an agent run or `agent_settled`                         | Distinguish command handling from a model turn; do not wait indefinitely for an event that is not expected |

`agent_end` is a low-level run boundary; the pinned contract permits retry or compaction afterward. `agent_settled` is the full-run boundary. The current fixture verifies ordinary settlement, cancellation, and a non-retried provider failure. Automatic retry/compaction continuations still need runtime-specific tests. `new_session` and `switch_session` also have a cancellation result that must be checked; successful RPC transport alone is not proof of a switch.

The fixture selects a custom Chat Completions model through `models.json`, supplies its key via an environment reference, and confirms replacement/append instructions in provider requests. See the [pinned custom-model format](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/docs/models.md). These are isolated native configuration checks, not yet a saved-profile configuration adapter or external-service acceptance.

## Project trust and extension boundaries

The fixture creates only its own project resources and extension. Without a saved trust decision, noninteractive RPC skips that project's `.pi/SYSTEM.md` and discovered extension. `--no-approve` keeps them unloaded; explicit `--approve` loads both for that launch. An unrelated decision in the isolated `trust.json` remains byte-for-byte unchanged. This verifies the pinned CLI behavior without editing the user's trust store.

The same probe runs the built-in `read` tool without any extension dialog, even with project resources denied. Project trust therefore cannot satisfy a requested per-tool approval policy. The [pinned Pi README](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/README.md) describes MCP and custom confirmations as extension concerns. No MCP extension is selected or verified here. A core Pi profile requiring MCP or universal tool approval must remain unsupported until a separately verified implementation can enforce it.

## Reproduce

Install the exact CLI version separately as described in the [initial probe report](engine-probe-2026-09-18.md), then run:

```sh
AGENT_MATRIX_TEST_PI=/absolute/path/to/pi \
AGENT_MATRIX_PI_REPORT=/absolute/path/to/report.json \
npm run probe:pi
```

The [recorded result](probes/2026-09-18-pi-rpc.json) uses a loopback HTTP fixture, synthetic credentials, private temporary home/config/session directories, and a temporary test project. It makes no external model calls. The test exercises the application RPC client and process supervisor, actual Pi tools, session files, extension dialogs, and trust behavior. It removes fixture state after confirmed cleanup. Report output is optional. Regular `npm run test` runs deterministic transport tests without executing the installed CLI.

Remaining work includes the immutable configuration adapter, native event-to-session mapping, actual Skill invocation, saved-profile launch, bilingual desktop acceptance, intended external endpoint/model/auth verification, retry/compaction handling, and other platforms. The existing shared runtime permission callback is not sufficient for Pi's select/confirm/input interactions; extend that boundary explicitly when connecting the adapter.
