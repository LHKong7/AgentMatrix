# Captured Skill source verification

Skill names are not sufficient evidence that a CLI selected the captured asset. OpenCode and Pi now compare native-discovered names and entry paths with the immutable adapter mapping before acknowledging a successful attachment. A same-name entry from another directory fails with a structured `skills` configuration diagnostic. This adds selected-source evidence to A5/A12/B6; complete native precedence and the delivery gates remain open.

## Engine-specific evidence

| Engine                      | Observation                                                      | Required match                                                                                                                                 | Receipt scope                                                                                                             |
| --------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| OpenCode 1.18.16            | `opencode debug skill` under the captured launch environment     | Each bound native name has exactly one entry at its captured `SKILL.md` path; unrelated native Skills are allowed                              | `opencode.skill-sources`: preflight in a separate native process. It does not inspect the ACP instance's cached selection |
| Pi 0.85.1                   | RPC `get_commands`, using each Skill command's `sourceInfo.path` | The entire Skill-command set matches captured names and entry paths; extension/prompt commands cannot shadow a selected `skill:<name>` command | `pi.skill-sources`: the attached RPC instance, checked on startup/resume and before and after turns                       |
| DeepSeek Harness 0.1.5-rc.2 | Existing composition readback only                               | No new runtime Skill-source check is claimed                                                                                                   | Unknown. DSH does not inherit another engine's source evidence                                                            |

Both adapters read their already captured mapping file and require a one-to-one set of asset IDs and native names. Every mapped entry must be in the manifest's captured file inventory. Matching accepts the exact selected absolute path or its canonical path obtained from the trusted captured entry. It never resolves or opens an arbitrary native-reported path. Plain Markdown assets use the generated frontmatter wrapper recorded by the adapter; the source check targets that native entry, not the unwrapped archival copy.

The native checks preserve their existing bounds. OpenCode private-command capture has a 4 MiB output limit and a 30-second deadline; the command may include unselected Skill contents, so all output stays in memory and is discarded after matching. Skill listings are bounded to 10,000 records and captured mappings to 1,000 bindings. Oversized, malformed, or missing source evidence fails as unavailable. No additional OpenCode process is launched for an empty Skill selection.

The OpenCode preflight uses the native loader during start/resume, so configured native plugins can initialize in that extra process. This follows the existing native configuration-readback trust boundary. Opening a configuration report never runs that preflight.

The selected file path is not proof of successful model invocation, model-visible prompt content, current in-memory bytes, or sandbox enforcement. OpenCode's pinned loader can load duplicate names concurrently, and its debug command runs separately from ACP. A matching preflight therefore cannot establish deterministic resolution of every collision in another process. The report states that limit explicitly. Pi's checks observe its current resource loader; trusted native extensions may still change behavior during a turn. Broader source inventories, collision reporting, and source changes outside the captured observation set remain separate work.

## Persistence and presentation

Successful adapters add a fixed check identifier to the durable Ready acknowledgment. The existing session observation ties it to the snapshot digest, process run, native session, and timestamp. Each Skill in the English/Chinese configuration report shows one of three states: a Pi RPC source match, a separate OpenCode-process preflight match, or no recorded native source check. The mapped native entry is shown separately from the asset's archival path, so a generated Markdown wrapper is not confused with its unwrapped source. This entry comes from verified captured inputs; report reads never execute a native discovery command. Prompt assets do not receive Skill evidence.

Old journals keep their existing meaning: `pi.skills` proves command-name discovery and `opencode.config` proves configuration mapping. Neither is upgraded to source verification. Historical observations remain historical after restart and failed attachment; a successful native resume records a fresh receipt. DSH continues to show unknown source verification. Existing saved/planned/bound asset revisions and immutable manifests are unchanged by report reads.

Failures contain only a fixed check category, reason, and `skills` field group. Native paths, native bodies, raw listings, headers, and credential values are excluded from the journal, report, and failure message. The captured paths and asset IDs already present in the configuration report retain their existing metadata boundary.

## Verification and sources

Unit checks cover same-name foreign and relative paths, duplicate/missing entries, unselected Pi Skills, shadowing commands, missing `sourceInfo`, malformed output, missing captured inputs, empty selections, legacy evidence, historical ownership, and engine separation. Installed native fixtures preserve the selected Skill name while redirecting its source and verify rejection without model requests. Normal fixtures still read captured Skill bodies and references and resume their native conversations.

Recorded macOS arm64 evidence: [OpenCode native source substitution](probes/2026-09-19-skill-sources-opencode-native.json), [Pi native source substitution](probes/2026-09-19-skill-sources-pi-native.json), and bilingual desktop reports for [OpenCode](probes/2026-09-19-skill-sources-opencode.json), [Pi](probes/2026-09-19-skill-sources-pi.json), and [DSH](probes/2026-09-19-skill-sources-dsh.json). The DSH fixture verifies that unsupported source evidence stays unknown while its existing lifecycle continues to pass. The Pi desktop fixture also verifies the separate mapped native-entry display.

The checks follow the pinned [OpenCode debug command](https://github.com/anomalyco/opencode/blob/v1.18.16/packages/opencode/src/cli/cmd/debug/skill.ts), [OpenCode Skill loader](https://github.com/anomalyco/opencode/blob/v1.18.16/packages/opencode/src/skill/index.ts), and installed Pi 0.85.1 `get_commands`/`SourceInfo` implementation. The upstream [Pi RPC reference](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md) describes the protocol; installed-release tests determine the contract supported here.

All provider fixtures are local and synthetic. These results do not establish external-provider compatibility, complete native source attribution, ACP-instance Skill identity for OpenCode, DSH source verification, or additional platform support.
