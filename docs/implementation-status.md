The active application reads/writes schema v2 through a single store. Existing v1 files migrate with exact-byte backups; browser preview retains its old v1 key. All nine configuration collections have compatible English/Chinese editors. Native CLI installations used for probes are not automatically registered as user profiles. Saving an installation path does not execute a CLI. The explicit desktop Check installation action probes OpenCode; only the pinned supported version enables ACP launch.

Latest verification: 273 unit tests, two opt-in installed-CLI ACP initialization/cleanup checks, an installed OpenCode runtime probe against a local protocol fixture (including two cancellation paths, native resume with retained history, permission persistence failure, override rejection, coordinator command replay, journal/event parity, and restart/resume), ESLint, TypeScript, production build, and changed-file formatting passed. Real Electron verification covers exact-byte v1 migration, all three engine drafts, shared connections/models, prompt and Skill revisions, directory capture/reimport, pinned/latest bindings, bundles, bilingual diagnostics, deletion cleanup, restart, and OS-encrypted credential creation/replacement/deletion. The native folder chooser is substituted in the smoke test; the actual import IPC, capture service, filesystem, and editors run unchanged. The configuration smoke uses synthetic credentials without executing agents. A separate [desktop session smoke](desktop-sessions.md) runs the installed OpenCode against a local synthetic provider, verifying explicit installation probing, profile-to-session capture, streamed/tool output, permission replies, both cancellation paths, renderer reload without resubmission, old/new shared-Prompt snapshots, app quit/restart, native resume, confirmed close, bilingual controls, escaped untrusted text, and journal key redaction. Neither fixture calls an external model provider.

The opt-in installed Pi probe additionally passes the [local RPC lifecycle fixture](pi-rpc.md), including Unicode streaming, tool context after native restoration, provider errors after acceptance, extension command handling without a model run, and unchanged unrelated trust decisions. Pi remains disabled in desktop session launch until its configuration/runtime adapters are connected and verified.

The installed DSH ACP lifecycle also passes separately through its pi-ai gateway component and native DeepSeek component, both against local Chat Completions fixtures. [Results](dsh-acp.md) establish the selected route's feasibility and its committed-output, usage, and replay limits. All three engines now have early local lifecycle evidence; this does not replace external provider or complete desktop acceptance.
